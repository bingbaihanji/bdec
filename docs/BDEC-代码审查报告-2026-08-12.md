## 中优先级问题

### M1. IrBuilder.createWriteVar — LVT flat map fallback 被移除

**文件：** `IrBuilder.java` 行 ~1616-1624

**问题：**
```java
// 旧代码（有 fallback）：
String lvtName = currentMethod.lookupVarName(slot, offset);
if (lvtName == null) {
    lvtName = currentLvtNames.get(slot);  // flat map fallback
}

// 新代码（无 fallback）：
String lvtName = currentMethod.lookupVarName(slot, offset);
// 如果 lookupVarName 返回 null，变量将失去名称
```

`lookupVarName(slot, offset)` 需要 LVT 中有匹配 PC 范围的条目。对于没有完整调试信息的 class 文件（或 LVT 不覆盖所有 PC 范围），会返回 null。之前的 `currentLvtNames.get(slot)` flat map fallback 保证了至少有一个名称可用。

**修复：** 恢复 flat map fallback：
```java
String lvtName = currentMethod.lookupVarName(slot, offset);
if (lvtName == null) {
    lvtName = currentLvtNames.get(slot);
}
```

### M2. BlockReducer LOAD case — varStoreSource 循环引用风险

**文件：** `BlockReducer.java` 行 2117-2124

```java
case LOAD -> {
    if (!insn.operands().isEmpty() && insn.operands().getFirst() instanceof Variable v) {
        Value storeSource = currentVarStoreSource.get(v);
        if (storeSource != null) {
            yield valueToExpr(storeSource);
        }
        yield varToExpr(v);
    }
    yield new VarExpr("var");
}
```

**问题：** 如果 `varStoreSource` 中 `Variable A → Variable B`，而 `Variable B → Variable A`（循环映射），`valueToExpr` 会无限递归。虽然在正常 IR 构建中不太可能出现循环，但没有保护。之前这个问题不存在，因为 LOAD case 不追溯 varStoreSource。

**修复：** 添加循环检测或将解析限制为一步：
```java
// 方案 A：仅解析一层（storeSource 是 InstructionRef 才追溯）
Value storeSource = currentVarStoreSource.get(v);
if (storeSource instanceof InstructionRef) {
    yield valueToExpr(storeSource);
}
yield varToExpr(v);

// 方案 B：添加 visited 集合防止循环
```

### M3. BlockReducer — CAST 临时变量提取过于激进

**文件：** `BlockReducer.java` 行 ~1745

```java
boolean needsTemp = op == IrOpcode.NEW_ARRAY
        || op == IrOpcode.INVOKE
        || op == IrOpcode.BINARY
        || op == IrOpcode.COMPARE
        || op == IrOpcode.UNARY
        || op == IrOpcode.ARRAY_LOAD
        || (op == IrOpcode.CAST && count > 1);
```

**问题：** `BINARY`, `COMPARE`, `UNARY`, `CAST(count>1)` 被引用 2 次时都会创建临时变量。但对于简单的 `a + b` 被用两次的情况，创建 `tmp0 = a + b` 反而降低了可读性。Java 源码中重复写两次 `a + b` 是正常的。

**影响：** 会导致不必要的临时变量声明，降低反编译输出的可读性。

**修复：** 仅对副作用指令（NEW_ARRAY, INVOKE, ARRAY_LOAD）创建临时变量。BINARY/COMPARE/UNARY 可以安全地被内联多次：
```java
boolean needsTemp = op == IrOpcode.NEW_ARRAY
        || op == IrOpcode.INVOKE
        || op == IrOpcode.ARRAY_LOAD;
```

## 架构层面评论

### 正面评价

1. **CAST 修复（BlockReducer LOAD case + ExpressionEmitter emitWithParens）是双层防御设计** —— IR 层面追溯 store 链 + 输出层面加括号。即使一处失败，另一处也可以兜底。这是正确的防御性设计。

2. **NEW_ARRAY 元素类型修复** —— 现在 IR 中存储数组类型而非元素类型，BlockReducer 在 NEW_ARRAY case 中从数组描述符提取元素类型。正确处理了 `new String[size]` 的渲染。

3. **泛型函数式接口类型重建（buildGenericFunctionalType）** —— 从 MethodType 常量池条目提取 SAM 描述符，重建正确的泛型参数。例如 `BiFunction + (Integer,Integer)Integer → BiFunction<Integer,Integer,Integer>`。这是解决 unnamedDemo 的关键一步。

4. **LambdaRewriter.buildLambdaParams 使用 Signature 属性** —— 从 Signature 属性获取泛型参数类型，替代擦除后的描述符类型。例如 `(Object,Object)Object → (Integer,Integer)Integer`。

5. **多引用临时变量提取（currentMultiUseTemps）** —— 解决了 DUP+NEW_ARRAY+AASTORE 模式中每个引用都内联为新表达式的问题。概念正确。

### 需要关注

1. **BlockReducer 行数仍在增长** —— 虽然之前做了拆分（ExpressionTranslator、IndyTranslator、BranchAnalyzer），但 blockReducer 仍在增长。`currentMultiUseTemps` 相关的预扫描逻辑（~50 行）可能应该提取到独立方法。

2. **IrBuilder 泛型推断是点对点修复** —— `inferGenericReturnType` 只处理 `Arrays.asList`，`buildGenericFunctionalType` 只处理 invokedynamic 的函数式接口类型。这是 CFR/Vineflower 常用的"模式匹配"方法，但随着支持的 API 增多，这类 hardcoded case 会膨胀。未来可能需要一个更通用的泛型传播框架。

3. **变量命名的两个路径存在分歧** —— IrBuilder 中 `lookupReadVar` 和 `createWriteVar` 对 LVT fallback 的处理不同：
   - `lookupReadVar`（行 689）保留了 flat map fallback：先 lookupVarName，再 currentLvtNames.get
   - `createWriteVar`（行 1619）移除了 flat map fallback：只用 lookupVarName
   
   这两个应该保持一致。
